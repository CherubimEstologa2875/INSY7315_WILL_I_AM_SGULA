# Requirements mapping (Jira WIL-153, Jira WIL-154)

The problem the practice faces is a lack of continuous development for clients outside of their therapy sessions, since the actual care a client receives is otherwise limited to the time spent face to face with Anat. The app also serves a second purpose for the practice, widening its reach to a broader community beyond the clients already attending sessions, since the daily broadcasts carry Anat's own therapy content out to any registered user, not only those under her direct care. Providing aftercare between sessions whilst also growing the practice's reach is the actual problem this app exists to solve for the client, and the mapping below is read against that, not just against a checklist of features.

This document maps the app's original functional requirements, taken from the hub documentation, together with the non-functional criteria from the module manual, to what has actually been built in the codebase, with the relevant files referenced throughout so that each requirement can be traced back to where it was implemented in the real app on `develop`.

## Functional requirements (Jira WIL-153)

| Requirement | Is It Built | Where |
|---|---|---|
| User management: register, login, profile update, password reset; Guest preview | Yes | This is built across `LoginFragment.kt`, `RegisterFragment.kt` and `PasswordResetFragment.kt` for the account flows, `SettingsFragment.kt` for the name and privacy toggles, and `GuestLandingFragment.kt` together with `SessionManager` for guest mode. The whole flow runs through real Firebase Auth rather than a prototype stub, using `repository.signIn`, `register` and `sendPasswordReset` directly. |
| Daily Broadcast: therapist uploads audio; users listen; history stored | Partial | The listening side of this requirement is built, `BroadcastFragment.kt` and `BroadcastHistoryFragment.kt` pull from `loadBroadcasts()` sorted by `publishedAt`, played through the same player used for the audio library. The admin upload side has not been wired through yet, since `AdminUploadFragment.kt` only validates a Broadcast date field whilst never calling `createBroadcast()`, a method that already exists in the repository layer but sits unused. |
| Mood Tracker: daily mood (1-5), notes, history/progress | Yes | `MoodLogFragment.kt` handles the five point Rough, Low, Calm, Good, Great scale with an optional note, and `MoodHistoryFragment.kt` shows the history, whilst every `MoodEntry` write is enforced server side through `firestore.rules`, which sets the `createdAt` timestamp itself rather than trusting the client. |
| Personal Journal: create/edit, prompts, secure storage, history | Yes | `JournalEditorFragment.kt` carries a daily rotating prompt through `JournalPrompts.kt` and rich text through `JournalMarkup.kt`, whilst `JournalHistoryFragment.kt` covers the history. Storage is owner only by rule, since the `JournalEntry` match block in `firestore.rules` has no `isAdmin()` clause whatsoever, a deliberate design choice that is tested directly in `journal.rules.test.js`. |
| Guided Meditation Quiz: weighted scoring, recommends category + broadcast | Yes | `QuizStartFragment.kt`, `QuizQuestionFragment.kt` and `QuizResultFragment.kt` carry the flow through, whilst the scoring and recommendation itself is handled through the `calculateQuizRecommendation` Cloud Function rather than client side logic. `QuizHandoff.kt` builds what the result screen passes on to the player, covered by `QuizHandoffTest` (Jira WIL-167). |
| Daily Affirmations: rotating motivational messages | Yes | Home reads today's line from `DailyBroadcast/current` through `loadDailyAffirmation()`, falling back to the `Affirmation` pool before the nightly function has first run. `refreshDailyAffirmation` picks from the whole pool at 00:05 South African time and never repeats the previous day's line, and admins add to the pool through `AdminAffirmationsFragment.kt`, capped at 200 characters in both the app and `firestore.rules` (Jira WIL-168). |
| Relaxation Music: white noise/nature tracks, favourites, background play, loop | Partial | The library, playback and loop are built across `AudioLibraryFragment.kt`'s three category tabs and `PlayerFragment.kt`'s MediaPlayer, with the loop toggle working as expected. The favourite star on `SgulaPlayerBarView` (`onToggleFavourite`, `isFavourite`) is present in the UI but has not been wired through, since `PlayerFragment.kt` never calls it and there is no field anywhere in the data layer to persist it, a gap found by searching through the entire data layer for any trace of it. |
| Virtual Succulent: grows with points, wilts after 7 days, one per user | Yes | `SucculentFragment.kt` and, as of this fix, `HomeFragment.kt` both read in real time from `observeSucculentState`. The stage thresholds match the spec exactly, Seed from 0 to 99, Sprout from 100 to 299, Growing from 300 to 599 and Blooming from 600 upward, whilst the wilt logic checks `lastActivityAtMillis` against a real seven day window in both places. |
| Notifications: FCM reminders, new broadcast alerts | Partial | This requirement is only built server side, since `sendWellnessReminder` exists as a Cloud Function whilst there is no `FirebaseMessaging` integration anywhere within the Android app, meaning nothing in the client registers for or displays a push notification. |

## Non-functional requirements (Jira WIL-154)

| Category | Evidence |
|---|---|
| Accessibility | The Jira WIL-96 audit went through every `ImageView` and `ImageButton` across all 48 layouts, each of which either carries a real `contentDescription` or is correctly marked `importantForAccessibility="no"` as decorative, with no unlabelled icons found. Touch targets within the mood, tab bar and plant stage components use the shared `sgula_min_touch_target` token of 48dp. |
| Responsive design | The Jira WIL-97 testing pass covers phone and tablet sizes on the Android layouts, whilst the website side carries real CSS breakpoints at 960px, 780px and 520px within `site.css`, together with a correct `viewport` meta tag. |
| Performance / feedback | Loading indicators serve as a shared pattern across the audio, journal, mood and admin screens rather than being handled ad hoc per screen. The succulent card updates live through a Firestore listener on `observeSucculentState` instead of polling, whilst the player shows a buffering indicator during both URL resolution and MediaPlayer preparation, and retries once automatically on a playback failure before surfacing an error to the user. |
| Security | Every collection within `firestore.rules` is gated by ownership through the `ownsDocument()` and `isAdmin()` pattern, with a deliberate absence of any admin override on `JournalEntry`. Write validation rejects backdated timestamps, out of range mood values and oversized journal entries at the rules layer itself rather than only on the client. This is covered by six rules test files in total, `journal`, `mood`, `quiz`, `userprofile`, and `audioSession` together with `guestAccess` added this session. |

## Known gaps, stated plainly

Three requirements are only partially built rather than complete: admin broadcast upload, audio favourites, and client side push notifications. These are real gaps that exist within the current codebase rather than oversights made whilst writing this document, since each one was found by searching through the actual code rather than assumed from the spec. It is worth deciding before the presentation whether these gaps should be closed in the time that remains, or whether they should be presented honestly as known scope cuts, since both are legitimate outcomes.
